# Implementation Plan: Realtime Risk Engine

**Branch**: `[010-risk-engine]` | **Date**: 2026-05-06 | **Spec**: [spec.md](./spec.md)  
**Input**: Feature specification from `/specs/010-risk-engine/spec.md`

## Summary

Introduce a backend rule-based Risk Engine that evaluates each backend-accepted realtime elevator state and generates traceable predictive-maintenance warnings for analytics. The engine uses deterministic rules for door blockage, active fault codes, thermal risk, vibration risk, and repeated overload, then feeds accepted warnings through the existing analytics repository and realtime publisher. This phase explicitly does not use `ai-service`; it creates a reliable baseline for later AI scoring.

## Technical Context

**Language/Version**: TypeScript 5.x, Node.js >=22  
**Primary Dependencies**: Express, existing Ditto realtime path, existing elevator contracts, existing `RiskAnalyticsService`, existing `RiskPublisher`, Vitest  
**Storage**: Existing in-memory risk warning repository for v1; no new persistent telemetry store in this phase  
**Testing**: Vitest unit/integration tests for rule evaluation, duplicate suppression, live-event integration, analytics readiness, and frontend analytics rendering  
**Target Platform**: Backend Node.js service plus existing React frontend dashboard  
**Project Type**: Web application with backend API/realtime service and frontend dashboard  
**Performance Goals**: Risk evaluation completes within the live-event processing path budget and does not delay visible elevator realtime updates by more than 100 ms per accepted state under local validation load  
**Constraints**: No frontend direct Ditto access; no `ai-service` dependency; warnings must preserve `{ modelVersion, validationRunId, modelTrace }` style traceability even when generated by deterministic rules; risk failures must not break elevator monitoring  
**Scale/Scope**: Initial building scope is existing L72 elevator fleet and simulator-driven validation; design should allow additional buildings and history-backed rules later

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Digital Twin authority**: Pass. The engine evaluates backend-normalized state derived from Ditto/Twin events. It does not read directly from devices or expose Twin access to the frontend.
- **Event-driven / reality-tolerant**: Pass. Evaluation is triggered by backend-accepted realtime updates. Late, duplicate, out-of-order, stale, and out-of-scope events are filtered before risk evaluation.
- **Governed data / schemas**: Pass. The feature reads `realtime` and `telemetry` elevator fields and writes `alarm`-class `RiskWarning` records with trace metadata.
- **Layered backend control plane**: Pass. Warning generation, persistence, authorization, and publication remain backend-mediated. The frontend only consumes analytics REST/realtime outputs.
- **Operational excellence**: Pass. Planning includes metrics, degraded readiness, integration tests, and failure isolation from elevator monitoring.
